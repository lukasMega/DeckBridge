Every deck DeckBridge can drive, generated straight from the device registry
(`ts/src/devices/registry.ts`), so it cannot drift from the code that talks to the
hardware. Looking for the values themselves — image spec, wire framing, key maps?
Those are on [Device specs](./device-specs.mdx).

:::caution[Platform status]
DeckBridge is **tested on macOS only**, and the GitHub releases ship **macOS builds
only**. Linux and Windows support exists in the code but is untested. "Untested"
below means no one has run DeckBridge against that physical deck — the model is
derived from a board that *was* tested, or from the reference implementations.
:::

## Devices in detail

### Stream Deck MK.2 \{#mk2}

Elgato's own 15-key deck. Driven natively over HID (no CORA emulation of the panel itself), so DeckBridge forwards the app's JPEG unchanged.

|  |  |
|---|---|
| **USB** | `0x0fd9`:`0x0080` `0x006d` `0x00a5` |
| **Keys** | 15 (5×3) |
| **Panel** | 72×72 JPEG |
| **Protocol** | `elgato-gen2` (elgato-hid driver) |
| **Tested** | — untested |

- `image.rotate` is still the Phase 0 default (0, passthrough). If keys come out upside down on real hardware, 180 is the other candidate — the CORA frames' native orientation has not been measured on an MK.2.
- The only non-Elgato-emulating model: `cora.usePhysicalIdentity` is true, so the deck's real serial and firmware version are forwarded to the app.

[Full spec →](./device-specs.mdx#mk2)

### Stream Deck Mini \{#mini}

Elgato's 6-key deck. BMP panel, not JPEG: the app's bitmap is forwarded as-is by the `format: 'bmp'` short-circuit in image-pipeline.

|  |  |
|---|---|
| **USB** | `0x0fd9`:`0x0063` `0x0090` `0x00b3` `0x00b8` |
| **Keys** | 6 (3×2) |
| **Panel** | 80×80 BMP |
| **Protocol** | `elgato-gen1` (elgato-hid driver) |
| **Tested** | ✓ tested (macOS) |

- BGR pixel order plus a 90° CW rotation, matching the reference 6-key implementation's `rotate + yFlip`.
- Fixed-size payload: 54-byte BMP header + 80×80×3 = 19254 bytes, 20 packets per key.
- Splash sources are upright, so the splash path overrides the transform to rotate 90 + flipH.

[Full spec →](./device-specs.mdx#mini)

### Mirabox 293V3 \{#mirabox-293}

The reference v3 board, and the device every other v3 model in this table is derived from. 15 JPEG keys at 112×112, 1024-byte CRT packets, press and release events.

**Also sold as:** HSV293SV3 / "293S V3" refresh (PID 0x1014)

|  |  |
|---|---|
| **USB** | `0x6603`:`0x1005` `0x1006` `0x1010` `0x1014` |
| **Keys** | 15 (5×3) |
| **Panel** | 112×112 JPEG |
| **Protocol** | `mirabox-cora` (mirabox driver) |
| **Tested** | ✓ tested (macOS) |

- Four PIDs: 0x1005 is the hardware-verified one; 0x1006 (EN variant) and 0x1010 (v2.5) come from the vendor's own PID tables; 0x1014 is the HSV293SV3 refresh. The last three are untested here.
- Upscales 72×72 CORA frames to 112×112, so it uses the `lanczos3` filter plus a 0.6 unsharp pass to claw back the softness.

[Full spec →](./device-specs.mdx#mirabox-293)

### Mirabox 293S Stream Deck \{#mirabox-293s}

The reference v1 board: physically 3×6 = 18 keys, of which the left 5 columns are exposed as a 15-key MK.2 and the right column becomes DeckBridge-native extra keys.

|  |  |
|---|---|
| **USB** | `0x5548`:`0x6670` |
| **Keys** | 15 (5×3) + 3 extra |
| **Panel** | 85×85 JPEG |
| **Protocol** | `mirabox-cora-v1` (mirabox driver) |
| **Tested** | ✓ tested (macOS) |

- Keydown-only firmware — the driver synthesizes the key-up event.
- The app sends MK.2-native 72×72 but the panel is 85×85, so the image is padded (pixels stay 1:1) with an edge-clamped border instead of being upscaled.
- Net image transform is the anti-transpose (rotate 90 ∘ flipV). The opendeck-akp153 guess of rotate90 + flipH + flipV reduces to a plain rotate270 and renders vertically flipped.
- The right column's wire ids (16, 17, 18) are derived from the opendeck-akp153 wire-id namespace, not hardware-verified.
- v1 firmware reports one hardcoded serial (`355499441494`) on every unit of every v1 model, so `sharedSerial` makes the settings key include the model id.

[Full spec →](./device-specs.mdx#mirabox-293s)

### Mirabox K1 Pro \{#mirabox-k1pro}

6 LCD keys (3×2) plus 3 rotary encoders, advertised to the Elgato app as a Stream Deck Mini. The encoders are not wired up — their input codes fall outside the key map and are dropped.

|  |  |
|---|---|
| **USB** | `0x6603`:`0x1015` `0x1019` |
| **Keys** | 6 (3×2) |
| **Panel** | 64×64 JPEG |
| **Protocol** | `mirabox-cora` (mirabox driver) |
| **Tested** | ✓ tested (macOS) |

- Report ID 0x04, not the 0x00 the rest of the family uses.
- Firmware drops the last byte of every full 1024-byte image chunk. `chunkPadByte` wire-encodes a sacrificial byte after every `packetSize - 1` payload bytes so the drop only ever eats padding — hardware-verified clean at q90–q100 for 2/3/5-chunk files.
- The app sends an 80×80 Mini BMP whose outer edge is dead border, so 6 px is cropped from every side before the 64×64 resize.
- JPEG must stay baseline with a single interleaved scan (the vendored jpeg-encoder fork), with the header through SOS inside the first 1023 payload bytes.

[Full spec →](./device-specs.mdx#mirabox-k1pro)

### Fifine AmpliGame D6 \{#fifine-d6}

Rev. 1 of the Fifine AmpliGame D6 (PID 0x0007) — the 293V3 board behind VID 0x3142, writing at 512-byte packets.

|  |  |
|---|---|
| **USB** | `0x3142`:`0x0007` |
| **Keys** | 15 (5×3) |
| **Panel** | 112×112 JPEG |
| **Protocol** | `mirabox-cora` (mirabox driver) |
| **Tested** | — untested |

- Not hardware-tested. The 512-byte packet size is inferred, and its own source called it surprising ("Not sure why, but it works with it"). `packetSizeCandidates` lets the HID report descriptor overrule it at open().
- Upstream runs this board at mirajazz v1 for writes but forces the event reader to v3, which is why the model is tagged `mirabox-cora` with `synthesizeKeyUp: false` rather than `mirabox-cora-v1`.
- `sharedSerial` is deliberately false. If two rev. 1 units ever collide on one settings key, setting it true on this model alone is the fix.

[Full spec →](./device-specs.mdx#fifine-d6)

### Fifine AmpliGame D6 (rev. 2) \{#fifine-d6-rev2}

Rev. 2 of the Fifine AmpliGame D6 (PID 0x0060) — the 293V3 board behind VID 0x3142, writing at 1024-byte packets.

**Also sold as:** "D6 Pro" in Fifine's own Windows software (the retail box just says D6)

|  |  |
|---|---|
| **USB** | `0x3142`:`0x0060` |
| **Keys** | 15 (5×3) |
| **Panel** | 112×112 JPEG |
| **Protocol** | `mirabox-cora` (mirabox driver) |
| **Tested** | ✓ tested (macOS, 2026-09-11) |

- Hardware-verified on macOS: enumerates via the 0xffa0/1 usage path, all 15 keys render full-bleed, press and release both map correctly.
- 512-byte writes render BLACK on this revision. The board reports `MaxOutputReportSize = 1024`, so every 513-byte write is discarded by the firmware while `write()` still returns success — the deck enumerates and reports presses while the screen stays black. Do not unify the packet size with rev. 1.
- The 112×112 panel size cannot be probed and the reference projects are split four ways (95 / 100 / 105 / 112). 112 is the value two independent owners derived from the hardware, and it holds up on a real unit.

[Full spec →](./device-specs.mdx#fifine-d6-rev2)
